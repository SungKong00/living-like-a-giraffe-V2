# 웹 화면을 토큰과 검증되는 컴포넌트로 구성한다

## Context and Problem Statement

관람 화면과 PC 스튜디오는 프레임워크 없이 DOM을 직접 만든다. 화면마다 버튼·입력·팝오버를 따로 만들고 한 CSS 파일에서 색·간격 값을 직접 적어, 같은 역할의 요소가 화면마다 다르게 보였다. 팝오버마다 문서 전체 이벤트를 따로 등록했고, 클래스 이름 하나만 틀려도 조용히 스타일이 빠졌다. 앞으로 화면을 늘려도 모양과 동작이 한 기준을 따라야 한다.

## Considered Options

- 지금처럼 화면별로 DOM과 CSS를 작성하고 리뷰로 일관성을 맞춘다.
- React 같은 UI 프레임워크와 외부 컴포넌트 라이브러리를 들인다.
- 프레임워크 없이 프로젝트 안에 디자인 토큰과 옵션을 검증하는 컴포넌트 팩토리를 두고, 화면은 그것만 조합한다.

## Decision Outcome

세 번째 방식을 채택한다. `web/ds/`에 토큰·기반 스타일·컴포넌트를 두고 화면은 `web/ds/index.js`에서만 가져온다. 컴포넌트는 옵션을 닫힌 스키마로 검증해 모르는 옵션·없는 variant·이름 없는 아이콘 버튼을 만들 때 바로 오류를 낸다. CSS는 `reset → tokens → base → components → views` 층으로 우선순위를 고정하고, 화면 CSS(`web/views/`)는 컴포넌트를 배치만 한다. 팝오버·메뉴의 바깥 클릭과 Esc는 오버레이 중재자 하나가 맡는다. 아이콘은 `lucide`, 글꼴은 `pretendard` 패키지를 번들해 외부 CDN 없이 제공한다. 사용법과 확장 절차는 [디자인 시스템 안내](../design-system/README.md)가 담당한다.

### Consequences

- Good, because 같은 역할의 요소가 모든 화면에서 같은 모양·키보드 동작·접근성 이름을 갖고, 잘못된 사용은 개발 중 첫 렌더에서 드러난다.
- Good, because Babylon 장면 코드와 편집 로직을 바꾸지 않고 화면 구성만 교체할 수 있다. 스튜디오 CSS는 스튜디오 청크에만 실려 휴대폰은 받지 않는다.
- Bad, because 새 모양이 필요하면 화면에서 바로 고치지 않고 컴포넌트 옵션과 문서를 함께 늘려야 한다.
- Bad, because 컴포넌트는 매번 DOM을 새로 만드는 방식이라 큰 목록의 부분 갱신은 화면 쪽 렌더 키 비교에 의존한다.
