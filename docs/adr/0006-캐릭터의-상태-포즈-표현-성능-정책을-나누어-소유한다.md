# 캐릭터의 상태·포즈·표현·성능 정책을 나누어 소유한다

## Context and Problem Statement

캐릭터는 수십 마리로 늘고 동작과 옷의 종류도 늘어난다. 지금은 `web/studio-characters.js` 한 파일이 자료실 파일 읽기, 캐릭터 만들기, 동작·경로 재생, 그림자, 고르기 등록, 움직임 제한을 모두 가진다. 움직임 제한의 수치(터치 기기 8개·그 밖 24개)는 `web/visitor-characters.js`에 있고, 장면을 계속 그릴지는 `web/scene.js`의 한 자리짜리 `keepDrawing`이 정한다.

2026-11-27에 잰 자산 규모는 다음과 같다. 두발 기린은 삼각형 15,416개·드로우 6회·관절 25개, 착용물을 든 네발 기린은 53,872개·23회다. 공개 월드 표본(`.world/sauna-regression/public.glb`)은 345,763개·21회다. 캐릭터마다 메시와 골격을 복제하므로 두발 기린 50마리는 드로우 300회로 월드의 14배다. 실제 기기의 프레임 시간은 아직 재지 않았다.

성능 대책(화면 밖 생략, 축소 단계, 이후의 인스턴스 그리기)을 지금 파일에 하나씩 더하면 편집과 관람이 같은 결과를 내는 성질과 새 동작·옷을 데이터만으로 더하는 성질이 함께 무너진다. 어느 책임을 어디가 가질지 먼저 정해야 한다.

## Considered Options

- 지금의 캐릭터 레이어에 성능 분기를 더한다.
- 관람 전용 캐릭터 레이어를 따로 만들고 편집 레이어는 그대로 둔다.
- 책임별로 나누고, 그리는 방식만 바꿔 끼울 수 있게 한다.

## Decision Outcome

세 번째 방식을 쓴다. 캐릭터 코드를 `web/characters/` 아래 다섯 책임으로 나눈다.

| 책임 | 소유하는 것                                                          | 모르는 것                    |
| ---- | -------------------------------------------------------------------- | ---------------------------- |
| 자산 | 모델·축소 단계·착용물·동작 파일 읽기, 보관, 해제                     | 장면에 놓인 캐릭터           |
| 상태 | 캐릭터마다의 자리·방향·시계·지금 동작과 섞는 비율                    | 메시와 그리는 방법           |
| 포즈 | 동작 표본·섞기·체형을 관절 값으로 바꾸기                             | 화면에 보이는지, 몇 마리인지 |
| 표현 | 관절 값을 화면에 그리기, 축소 단계 바꾸기, 착용물·그림자·고르기 등록 | 경로와 시간표                |
| 정책 | 화면에 보이는지, 어느 축소 단계인지, 기기에 따른 한도                | 동작과 경로의 내용           |

장면을 계속 그릴지는 `web/scene.js`가 소유하고, 요구하는 쪽이 여럿 등록한다.

첫 번째 방식은 변경이 가장 작지만 수치와 분기가 여러 파일에 흩어진다. 두 번째 방식은 관람을 빨리 고칠 수 있지만 경로·체형·동작 섞기를 두 번 구현하게 되어 [캐릭터 경로 설계](../../openspec/changes/walk-character-routes/design.md)가 정한 "편집과 관람이 같은 결과"를 지키기 어렵다. 구현 계획은 [캐릭터 성능 설계](../../openspec/changes/scale-character-performance/design.md)에 둔다.

### Consequences

- Good, because 성능 수치(화면 크기 경계, 기기 한도)와 판단이 정책 한 곳에만 있어, 대책을 하나씩 끄고 같은 장면에서 비교할 수 있다.
- Good, because 표현을 지금의 복제 방식에서 인스턴스 방식으로 바꿔도 상태·포즈·경로·체형이 그대로다. 편집 장면은 복제 방식을 계속 쓸 수 있다.
- Good, because 새 동작·옷·축소 단계는 자료실 파일의 규약으로 더한다. 종류가 늘 때 코드를 고쳐야 한다면 경계가 잘못된 것이다.
- Bad, because 상태와 포즈는 화면에 보이는지를 묻지 않으므로, 화면 밖 생략은 정책이 정하고 조립하는 쪽이 전달해야 한다. 호출 단계가 하나 늘어난다.
- Bad, because 관람 카메라의 방향 고정과 직교 투영이 전제가 된다. 화면 크기 하나로 모든 캐릭터의 축소 단계를 정하는 방식은 원근 투영에서, 빌드 때 안 보이는 면을 지우는 이후 대책은 회전을 다시 허용하면 쓸 수 없다.
- Bad, because 책임을 나누는 동안 `web/studio.js`·`web/studio-versions.js`·`web/visitor-characters.js`가 쓰는 `characterLayer()`의 모양을 유지해야 하므로, 옮기는 일과 동작 변경을 같은 커밋에 섞지 않는다.
